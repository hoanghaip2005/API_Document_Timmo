Tài liệu API Backend Nail Salon

Bản bàn giao cho team đấu nối platform. Tài liệu ưu tiên tiếng Việt dễ hiểu, chỉ giữ nguyên tên biến, đường dẫn và giá trị trong code vì đó là hợp đồng kỹ thuật mà frontend, HRM hoặc module khác phải gọi đúng.

Ngày cập nhật: 2026-06-06. Nguồn đối chiếu: route backend trong NailSalonManagementSystem-Backend/src, Postman collection, GitNexus và cách trình bày API tham khảo từ Nhanh.vn/Zalo Developers.

2. Cách gọi API

Thành phầnDùng khi nàoGiải thích dễ hiểu
Authorization: Bearer <accessToken>Gần như mọi API sau khi đăng nhập.accessToken giống vé vào cửa ngắn hạn. Hết hạn thì lấy vé mới bằng refresh token.
Authorization: Bearer <firebaseIdToken>Chỉ dùng khi gọi /admin/signin, /auth/signin, /auth/change-password.Đây là token do Firebase cấp sau khi người dùng đăng nhập Firebase.
X-Firebase-AppCheckKhi backend bật App Check ở chế độ bắt buộc.Dùng để chứng minh request đến từ app hợp lệ, không phải script ngoài.
X-Idempotency-KeyKhi gọi API ghi dữ liệu: tạo/sửa/xóa.Giúp tránh tạo trùng nếu người dùng bấm gửi hai lần hoặc mạng retry.
If-None-MatchKhi endpoint trả ETag.Nếu dữ liệu chưa đổi, backend trả 304 để giảm tải.

3. Đăng nhập và token

Luồng đúng

  1. App đăng nhập Firebase để có firebaseIdToken.
  2. Gọi POST /api/v1/auth/signin hoặc POST /api/v1/admin/signin.
  3. Backend trả accessToken và refreshToken.
  4. Gọi API nghiệp vụ bằng Authorization: Bearer <accessToken>.
  5. Khi access token hết hạn, gọi POST /api/v1/auth/refresh-token với body chứa refreshToken để lấy access token mới.
{
  "jwtToken": "Bearer <backend-access-token>",
  "accessToken": "Bearer <backend-access-token>",
  "refreshToken": "Bearer <backend-refresh-token>",
  "tokenType": "Bearer",
  "sessionId": "sess_...",
  "expiresAt": 1790000000000,
  "accessTokenExpiresAt": 1790000000000,
  "refreshTokenExpiresAt": 1792592000000,
  "user": {
    "uid": "user_...",
    "email": "owner@example.com",
    "role": "owner",
    "shopId": "shop_..."
  }
}
TokenDùng để làm gìCó tốn Firestore reads không?
accessTokenGọi API nghiệp vụ sau khi đăng nhập.Bản thân bước kiểm tra token không đọc Firestore. Reads đến từ API nghiệp vụ phía sau.
jwtTokenBí danh cũ của accessToken.Không phát sinh thêm read. Giữ để module cũ không vỡ.
refreshTokenChỉ dùng để xin access token mới.Không đọc Firestore trong flow hiện tại; backend kiểm tra JWT nội bộ và cache revoke.
Không gọi /auth/signin trước mỗi API. Đăng nhập có đọc user và cập nhật lastLoginAt; còn access token/refresh token được thiết kế để giảm việc đọc DB không cần thiết.

4. Từ điển biến và bí danh

Các biến dưới đây xuất hiện nhiều trong request/response. “Bí danh” nghĩa là hai tên khác nhau nhưng backend hiểu cùng một ý để giữ tương thích với app cũ.

branchIdMã chi nhánh/cửa hàng con.Branch, service, attendance, closing, report.Owner phải gửi khi chọn chi nhánh; employees thường lấy từ token.

workDateNgày làm việc theo quy tắc chốt ngày.Attendance, settlement, report.Không luôn giống ngày lịch nếu chi nhánh có giờ chốt sau nửa đêm.

6. Hàm xử lý chính

Phần này giúp người đọc hiểu “function” trong code đang đóng vai trò gì. Đây không phải API public, nhưng là nơi quyết định cách dữ liệu được kiểm tra, tính toán và trả về.

verifyFirebaseAppCheckKiểm tra App Check nếu backend bật.Có thể chặn request trước khi vào API nghiệp vụ.
createIdempotencyMiddlewareChống gửi trùng request ghi dữ liệu.Cùng key + cùng body có thể trả lại kết quả cũ; cùng key + khác body trả lỗi 409.

buildAttendanceDiscountTính số tiền discount của attendance.V2 nên chỉ lưu số discount ở attendance; phân bổ chủ/nhân viên để lúc chốt ngày.
buildWorkDaySettlementPreviewTính thử kết quả chốt ngày.Quyết định employeeSummaries, ownerDiscountSupported, tổng tiền chủ và nhân viên.
get-session-settlementsTạo danh sách card chốt sổ nhiều ngày.Dùng cho màn danh sách chốt sổ trước khi vào detail.

8. Mẫu gọi API

Đăng nhập owner hoặc nhân viên

curl --request POST "{{baseUrl}}/api/v1/auth/signin" \
  --header "Authorization: Bearer {{firebaseIdToken}}"

Lấy access token mới

curl --request POST "{{baseUrl}}/api/v1/auth/refresh-token" \
  --header "Content-Type: application/json" \
  --data '{ "refreshToken": "Bearer {{refreshToken}}" }'

Xem trước chốt sổ ngày

curl "{{baseUrl}}/api/v1/employee/session/settlement-preview?branchId={{branchId}}&workDate=2026-05-18&ownerDiscountCoverageRate=50" \
  --header "Authorization: Bearer {{accessToken}}"

Tạo báo cáo tuần

curl --request POST "{{baseUrl}}/api/v1/weekly-report" \
  --header "Authorization: Bearer {{accessToken}}" \
  --header "Content-Type: application/json" \
  --data '{ "branchId": "{{branchId}}", "weekStartDate": "2026-05-18" }'

10. Kiểm thử khi đấu nối

  • Luôn kiểm tra cả mã HTTP và type/message trong body lỗi.
  • Với API có ETag, gọi lần đầu lấy ETag, gọi lại với If-None-Match để kỳ vọng 304.
  • Với API ghi dữ liệu, dùng X-Idempotency-Key khi retry để tránh tạo trùng.
  • Không xóa alias cũ như jwtToken, storeId, amount, images, payType nếu module khác còn đọc.
  • Flow V2 không chọn nhân viên chịu discount. Nếu thấy request mới gửi selectedEmployeeUserIds hoặc discountEmployeeScope=selected thì xem là flow cũ cần dọn ở frontend.
  • Role chuẩn trong DB/API là employees. Không tạo user mới với role staff.
  • Báo cáo tháng nên ưu tiên weekly-report; chỉ dùng legacy owner-summary để đối chiếu hoặc khi cần debug.
